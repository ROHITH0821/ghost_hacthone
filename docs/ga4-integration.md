# Optional Google Analytics integration

## Architecture audit and implementation plan (before implementation)

Ghost uses Next.js App Router, React, Tailwind and TanStack Query. Dashboard APIs authenticate through the existing approved OTP/JWT session and resolve the database user. Prisma/PostgreSQL stores users, owner-only agency workspaces, clients, websites (`Site`) and audit missions. A site belongs to a user and may belong to an agency client; it is the correct integration boundary. No new identity or workspace permission model is needed.

Audits crawl a website into a ContextPack, discover flows, simulate shopper journeys, aggregate findings, calculate the deterministic six-dimension Ghost Score, then generate fixes. The adapter creates a GhostReport stored in Mission.report. Results share IntelligenceReportView; PDFs have a separate HTML composer. Anthropic is the existing LLM provider. Audit execution and PDF/email finalization have authenticated endpoints and bounded Vercel cron recovery. Local crawls may be cached on disk; dashboard queries are cached in the browser; completed reports are database snapshots.

Plan: add a site-scoped external-source connection and short-lived OAuth attempt; isolate Google API/normalization code under data-sources/ga4. Server-side OAuth uses analytics.readonly, state, browser binding, PKCE and encrypted refresh tokens. Explicit property AND web-stream selection precedes a real scoped reporting query. A cached normalized snapshot is the only analytics input to audit enhancement. No Google calls on dashboard GET or mandatory analytics calls during audits. Website-only pipeline, scoring and baseline findings stay unchanged. Optional evidence links exact page paths to existing findings, gives transparent traffic ordering within severity, and separates measurements, computed observations, constrained AI interpretation and recommendations.

Security review identified public archived PDF storage. Public archives must strip the optional evidence field; enriched PDFs are authenticated, on-demand and never uploaded there. Connections are authorized by Site.userId; callback attempts are bound to both user and website. Disconnect deletes credentials/cache/pending grants, best-effort revokes Google access, and preserves dated evidence in historical reports. Reports must not claim that page traffic measures the number of people affected by a discovered issue.

Implementation/validation and deployment details follow below.

## Traffic-aware AI pipeline (September 2026)

The approved pipeline extension reuses `AnalyticsSnapshot` and the existing cached `getSnapshotForSite` lookup. After crawling, `ghost-api` resolves the mission's site and loads the cache once. Missing sites, missing snapshots, an existing `reliable: false` flag, or lookup/normalization errors produce `null` traffic context and the normal website-only audit. This step does not refresh GA4 or call Google.

`traffic-supplement.ts` is a thin allowlist: source, date range, selected summary metrics, at most fifty pages sorted by views, ten acquisition sources sorted by sessions, device/session rows, and a verified-revenue availability flag. No property/stream identifiers, credentials, event lists or internal connection metadata enter the AI context. Missing metrics remain null; absent/unknown key-event configuration also keeps key-event rates unavailable. Pages present only in landing data have null views. Multiple source rows collapsing to the same normalized path are conservatively unavailable for that dataset; they are not summed or averaged without a verified aggregation.

Stage 1.5 (flows) and Stage 2 (personas) remain unchanged and receive no analytics. Stage 3 gets the supplement in a third user content block. Its instructions add traffic scale to severity, affected AI journeys and flow importance; no numerical priority formula or weights were introduced. Stage 4 receives only its matched page and the source/date range. An unmatched finding uses the original fix prompt. The first two content blocks and the entire website-only system prompt are unchanged. GA4 strings remain untrusted evidence; quantitative claims must cite GA4 and the supplied period. Traffic is potential reach, not a measured count of people affected. Publishable draft variants must not contain private analytics.

The shared `normalizePath` strips query/fragment and trailing slashes from URLs or paths, preserves path case, and rejects non-path labels. Engine fixes and report evidence use the same matcher: explicit affected page first (the report adapter retains this in `category`), then direct paths and existing path-name/keyword/homepage fallbacks. Ambiguous fallback candidates and explicit pages absent from the cache remain unmatched. No UI, PDF, report loader or score changes are part of this extension.

**Score and revenue:** scoring continues to use only crawl, flow and persona inputs. `hasVerifiedRevenue` requires a reliable snapshot with both non-null purchase/revenue fields; it is informational, not permission to estimate losses. `validate-output.ts` is unchanged and forces `monthly_low = monthly_high = 0`, even when purchase totals exist. No loss estimation is implemented because purchase totals do not establish loss caused by an obstacle.

**Verification:** the new `tests/ga4-traffic-supplement.test.ts` covers mappings/caps, nulls, normalization, ambiguous matches, shared report matching, exact website-only prompt compatibility, stage isolation, compact per-finding requests, lookup failure fallback, and identical complete Ghost Score output for the same crawl/persona fixtures. LLM transport is mocked; these tests do not certify live model ranking quality or a live Google OAuth connection.

**Inherited limitations requiring release review:** this extension intentionally preserves the existing sync/cache and rendering architecture. The report overlay reads the current cache, which can differ from the snapshot used during an older audit. The existing `reliable` flag is accepted as provided; this extension does not add Google response-quality validation or freshness policy. Existing PDF delivery can upload reports to public storage, including analytics-enabled output; access/retention controls need review before using confidential client data. The architecture-plan privacy intent above is not a claim that private PDF delivery has been implemented here.

Validation run for this extension: `npm run typecheck` passed; `npm test` passed all 40 tests (28 existing and 12 new), with no skips. `git diff --check` passed. Both pipeline paths were exercised with mocked Anthropic transport; no live Google or paid LLM calls were made. Live ranking quality and Google setup still require environment-specific verification.

## Connect during new audit setup

The existing Google Analytics card now appears in **Your goals** and **Review & start**. It checks the entered URL against the signed-in owner's sites without creating a site on page load. Clicking Connect saves/reuses that owner's website and opens Google consent in a popup. The form (URL, client, audit depth, goals and fix selection) stays mounted. The authenticated callback posts a result only to the configured app origin; the parent verifies both origin and popup identity, then opens inline property selection. Denial, a closed/blocked popup, unavailable GA4 configuration or failed status lookup does not prevent a website-only audit.

OAuth completion uses an exact state hash scoped to the signed-in owner, a short-lived HttpOnly flow cookie, and atomic attempt consumption. Pending refresh tokens are now encrypted with the attempt ID as their binding; earlier in-progress OAuth attempts must be restarted after deployment. Property selection awaits the initial sync so a successful first sync is available when the audit starts. If that sync fails, the card exposes the error and offers a retry; the audit can still proceed without analytics.

Local browser regression: `node scripts/ga4-audit-ui-review.mjs` (start Next on port 3010 first). This uses installed Chrome by default, a temporary fixture route removed on exit, and intercepted APIs/Google consent. It never creates a real audit or modifies a Google account.
